# Real student usability test protocol

This protocol is a collection plan, not evidence of completed testing. Do not mark a result as passed until a real participant completes the task and the note is written immediately afterward.

## Participants

- Recruit 3–5 high-school or college students who are not the builder.
- Prefer at least two people with no web-development experience.
- Explain that the session tests the product, not the participant; ask for consent before recording notes, screen or quotations.
- Use a pseudonym or participant number in the notes. Do not store student identity, school, email or recordings in the public repository.

## Task script

Give the participant only this goal: “Use this board to turn a real research question from one of your classes or student activities into a one-page evidence brief.” Do not explain the controls first.

1. Start from a fresh browser and describe what the page appears to be for.
2. Add one question card with an owner and a smallest next step.
3. Register one public source with its publisher, URL, access date, unit and limitation.
4. Add a card linked to that source and move it through the evidence flow.
5. Complete the verification checks that the evidence actually supports.
6. Edit the headline, takeaway and caveat, then export Markdown.
7. Back up the board, change the headline, restore the backup and confirm the old headline is visible again.
8. Repeat the core path on a phone-sized screen.

## Record after each session

- Completion: which numbered task was finished without help.
- Time: seconds to first card, source registration and final export.
- Friction: the first point of hesitation, error or request for help.
- Language: one verbatim quote about what was clear or confusing, with permission before publication.
- Outcome: what changed in the product after this session and why.
- Honesty check: do not describe a hypothesis, prototype reaction or one participant's opinion as measured impact.

## Minimum evidence for the submission

Keep the raw notes private. Publish only an anonymized summary with the number of participants, task completion counts, recurring friction, the resulting product change and approved quotations. If no participant completes the session, leave the user-validation claim unchecked.
